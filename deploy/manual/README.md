# Production GitHub Actions delivery

`.github/workflows/deploy-production.yml` runs on `main` push or manual dispatch from `main`. It repeats lint, tests, build and archive checks before any SSH use. Configure repository secrets `VPS_HOST`, `VPS_USER` (`deploy`), `VPS_SSH_KEY` and `VPS_KNOWN_HOSTS` with the independently verified VPS host key. Keep the private key out of Git and artifacts. A missing secret fails before the first SSH call. Do not enable this workflow until the existing Vultr target, Nginx permissions and least-privilege sudo rules have been reviewed.

Static releases only change `/opt/ducmy/web/current`; Nginx already reads through that symlink, so the deployment scripts never call `sudo` or reload Nginx. The `deploy` user must own `/opt/ducmy/web` (including `incoming`, `releases`, and `deploy.lock`). Nginx must be able to traverse `/opt/ducmy/web` and read each release's files. Verify this once during VPS setup; do not grant `777` permissions. A failed smoke check restores the previous symlink and verifies the served index and asset bytes. A same-SHA retry only accepts the identical archive and tree. Nginx configuration changes remain a separate operator task, outside this release workflow.

The job uploads a SHA-named archive, checksum and the matching release helpers to `/opt/ducmy/web/incoming/<SHA>`. The release helper checks the checksum, validates archive members, creates an immutable release under `releases/<SHA>`, switches `current` atomically, and compares the actual localhost HTTP index and asset bytes to that release. A failed smoke restores and verifies the old symlink when one exists. An identical archive can be retried; a different or incomplete existing release is rejected. No old release is deleted. Successful Actions logs include `Web release active: <SHA>`; a mere CI artifact is not proof of deployment.

Before enabling, verify Nginx (`www-data`) can traverse `/opt`, `/opt/ducmy`, `/opt/ducmy/web` and `/opt/ducmy/web/releases`; the helper sets the latter two to mode 755 and all new release files to readable modes. Existing parent permissions need an operator check. No Nginx reload or sudo permission is required for static release switching. Rollback a known release with `deploy/manual/web-rollback.sh` on the VPS; do not remove the current release. If the VPS fails entirely, restore the server from the operator's Vultr backup, then verify DNS/tunnel, Nginx, Web files, API and MariaDB before reopening traffic.

The existing `ci.yml` remains CI-only. GitHub Actions `workflow_dispatch` must be started from `main`; pushes to any other branch do not deploy. Build-time `VITE_API_URL` and `VITE_SITE_URL` are production values in the workflow, so changing domains requires a reviewed workflow update and a new Web release.
